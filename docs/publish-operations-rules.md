## 1. Cloudflare 公開時・運用時の高額請求防止ルール

目的: 使っていないアプリ、自動処理のループ、大量アクセスなどによる想定外の請求を防ぐ。

前提: まず読み取り専用で調査し、設定済みと推測しない。

### 1-1. 課金対象を一覧にする

静的 Pages、Pages Functions／Workers、Durable Objects、D1、KV、R2、Queues、Cron、AI、ログ、外部 API を分け、契約プラン、無料枠、従量料金を確認する。
「Pages だから無料」「月 5 ドルが総額上限」と判断しない。

### 1-2. 放置しても動く処理を調べる

Cron、Durable Objects の alarm、キュー、定期取得、自己呼出し、再試行、再投入を点検する。
実行回数・頻度・同時実行・再試行に制限を設ける案を出す。
処理が成功または不要になったら終了する設計を確認する。未使用の試作アプリも含める。

### 1-3. 高コスト処理の入口を守る

AI 生成や大量 DB 処理には、必要な認証、ユーザー別・全体の利用枠、流量制限を検討する。
外部 API 呼出し前に利用枠を確認し、連打・再送・並列実行による超過を考慮する。
WAF や rate limit だけで請求総額を保証しない。

### 1-4. 処理制限と金額上限を区別する

Workers の CPU 制限は通常処理の実測に基づき提案する。これは 1 回の処理の制限であり月額上限ではない。
外部 AI のモデル、入力・出力長、回数、リトライ、代替モデルの費用も別に確認する。
支出制限機能の対象・例外・反映遅延も確認する。

### 1-5. 通知だけに頼らない

製品・プランで利用できる通知、通知先、到達確認、確認担当を整理する。
「通知が来る」と「課金が自動停止する」は別。予算・停止基準はオーナー（ひろみん）に確認する。
利用できない機能を設定済みとしない。

### 1-6. 緊急停止手順を用意する

公開 URL だけでなく、Cron、alarm、Queue の投入元と処理側、他サービスからの呼出し、プレビュー URL も対象にする。
どの画面で何を止めるか、復旧方法も記録する。停止後は新規実行・利用量が減ったことを確認する。
データ削除を勝手に行わない。

### 1-7. 公開前後に検証する

通常操作、連打、エラー、再試行、同時実行、停止後の状態を、低コストの試験で確認する。高額な負荷試験は禁止。
公開後のリクエスト数、CPU、DB 操作、Queue 滞留・再試行、外部 AI 利用額の確認担当とタイミングを決める。
MD に書いただけで常時監視が動いているとは扱わない。

### 1-8. 承認前に本番を変えない

調査結果、危険箇所、修正案、設定差分、想定費用、停止・復旧手順を先に報告する。
指示だけで本番公開、有料化、契約・権限・本番設定変更、既存アプリ停止、データ削除を実行しない。必要な変更は承認後に行う。
秘密のキーやトークンを MD、ログ、Git へ書かない。

## 2. このリポジトリの現状（2026-10-22 読み取り専用調査）

リポジトリ内のファイルだけを調べた結果。Cloudflare ダッシュボード側の設定は見ていない。

### 2-1. 確認済み（リポジトリ内で確認できたこと）

| 項目 | 結果 |
| --- | --- |
| 構成 | jpg 192 枚、`index.html` 1 枚、`README.md` 1 枚。コードは `index.html` のみ |
| 配信元 | `index.html` 内の URL はすべて `https://cdn.jsdelivr.net/gh/pipasol87-maker/-sakuya-images@main/...`（jsDelivr 経由の GitHub 配信） |
| JavaScript | URL 欄クリックでクリップボードにコピーする `onclick` だけ。`fetch` や外部 API 呼出しはない |
| Cloudflare 設定ファイル | `wrangler.toml` / `wrangler.json` / `functions/` / `_headers` / `_redirects` / `_routes.json` / `.dev.vars` のいずれも存在しない |
| 放置して動く処理 | Cron、alarm、Queue、定期取得、GitHub Actions（`.github/` なし）のいずれもない |
| 高コスト処理 | AI 生成、DB 操作、外部 API 呼出しはない |
| 秘密情報 | トークンや API キーらしき文字列はリポジトリ内にない |
| リポジトリ容量 | 作業ツリー 42 MB、最大ファイル 624 KB（`stock2026/top/img_6020.jpg`） |

jsDelivr の公式 README（github.com/jsdelivr/jsdelivr）で確認した制限:

- 「Packages larger than 150 MB or single files larger than 20 MB (in the case of GitHub) are not supported by default.」
- ブランチ参照（`@main`）のキャッシュは 12 時間。コミットハッシュやタグ指定は実質無期限。

このため、画像を追加し続けて 150 MB を超えると jsDelivr 配信が止まる可能性がある。これは請求ではなく「表示が消える」リスクなので、容量が 100 MB を超えたら分割や別配信を検討する。

### 2-2. 未確認（リポジトリからは分からないこと）

- Cloudflare アカウントにこのリポジトリを接続した Pages プロジェクトがあるか。
- Cloudflare 上に他のプロジェクト（試作アプリ、Workers、Cron 付きのもの）があるか。
- 契約プラン（Free / Workers Paid など）、無料枠、従量料金の現在値。公式ドキュメントはこの調査環境のネットワーク制限で取得できなかったため、数値はここに書いていない。
- 利用できる通知の種類、通知先メール、支出制限の有無。
- jsDelivr は無料 CDN だが、利用規約・制限は変わりうる。年に 1 回は上記 README を見直す。

### 2-3. 承認が必要（この調査では実行していないこと）

- Cloudflare ダッシュボードへのログインと設定の確認・変更。
- このリポジトリの `main` への変更（このルール文書のマージを含む。`main` は jsDelivr の配信元）。
- 既存アプリの停止、プランの変更、データ削除。

## 3. Cloudflare に新しく何かを公開するときの手順

1. 本ファイルの 1 章を読み、公開するものを 1-1 の区分で一覧にする。
2. Cloudflare ダッシュボードで現在のプランと、既存プロジェクトの有無を**実際に見て**記録する（推測しない）。
3. 1-2〜1-4 の観点で危険箇所と修正案を書き、1-6 の停止・復旧手順を先に用意する。
4. 調査結果・設定差分・想定費用をオーナーに報告し、承認を得る。
5. 承認後に公開し、1-7 の低コスト試験と公開後の確認担当・タイミングを決める。
6. 本ファイルの 2 章を更新する。確認済みと未確認を混ぜない。

対策があることと、請求が絶対に増えないことは別物として書く。
